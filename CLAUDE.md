# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Marketing/landing site for Omixir Bioinformatics, built with TanStack Start (React 19 + file-based
routing), TypeScript, and Tailwind CSS v4. Managed via [Lovable](https://lovable.dev) — commits
pushed to the connected branch sync back into the Lovable editor.

Package manager is **bun** (see `bun.lock`, `bunfig.toml`), though scripts are also runnable via npm.

## Commands

- `bun run dev` (or `npm run dev`) — start the dev server (vite dev)
- `bun run build` — production build
- `bun run build:dev` — build in development mode
- `bun run preview` — preview a production build
- `bun run lint` — ESLint over the whole repo
- `bun run format` — Prettier write

There is no test suite configured in this repo.

## Important constraints

- **Never rewrite published git history** (no force push, no rebase/amend/squash of pushed commits)
  — this repo is synced with Lovable, and history rewrites break the sync and can lose the user's
  project history in the Lovable editor.
- `bunfig.toml` enforces a 24h supply-chain guard (`minimumReleaseAge`) on new package installs.
  Only a fixed allowlist of `@lovable.dev/*` packages bypasses it; adding to that allowlist needs
  explicit user confirmation.
- `vite.config.ts` wraps `@lovable.dev/vite-tanstack-config`, which already wires up TanStack
  devtools, `tanstackStart`, `viteReact`, `tailwindcss`, `tsConfigPaths`, nitro (Cloudflare target),
  `VITE_*` env injection, the `@` path alias, React/TanStack dedupe, error-logger plugins, and
  sandbox port/host detection. **Do not re-add any of these manually** — duplicate plugins break
  the app. Extend config only via the `vite`/other keys passed to `defineConfig`.
- `src/routeTree.gen.ts` is auto-generated by the TanStack router plugin — never hand-edit it.

## Architecture

### Routing (TanStack Start, file-based)

Routes live in `src/routes/`; see `src/routes/README.md` for the full convention table. Key points:

- One root layout: `src/routes/__root.tsx` (defines `<html>` shell, head tags/SEO meta, global
  `SiteHeader`/`SiteFooter`, the React Query provider, and the 404/error boundary components).
- No `src/pages/`, no `_app/index.tsx`, no `app/layout.tsx` — those are Next/Remix conventions and
  don't apply here.
- Dynamic segments are bare `$id`, optional segments are `{-$category}`, splats are `$.tsx` (read
  via `_splat`, never `*`).
- Nested product pages follow the `products.tsx` (layout, just an `<Outlet />`) +
  `products.assure.tsx` / `products.geneie.tsx` flat-file convention rather than a `products/`
  directory.
- `src/routes/sitemap[.]xml.ts` is a server route (`Route.server.handlers.GET`) that hand-generates
  `sitemap.xml` from a static list of entries — update this list when adding/removing pages.
- `src/router.tsx` creates the router + a `QueryClient`, exposed via router context
  (`{ queryClient }`), consumed in `__root.tsx` via `Route.useRouteContext()`.

### SSR error handling (defense in depth, three layers)

This app has non-obvious layered error handling to survive server-side failures that would
otherwise show a raw/blank error to users:

1. `src/start.ts` — a TanStack Start server middleware (`errorMiddleware`) that catches thrown
   errors without a `statusCode` and returns a styled fallback HTML page instead of a raw 500.
2. `src/server.ts` — the Cloudflare Worker `fetch` entry. It wraps the whole SSR handler in
   try/catch, AND separately detects the case where **h3 has already swallowed an in-handler throw**
   into a generic `{"unhandled":true,"message":"HTTPError"}` JSON 500 (try/catch alone can't catch
   that, since h3 converts it before it propagates) — see `normalizeCatastrophicSsrResponse`.
3. `src/lib/error-capture.ts` — installs global `error`/`unhandledrejection` listeners that stash
   the _original_ Error out-of-band (5s TTL) so `server.ts` can recover a real stack trace/message
   even after h3 has swallowed it into the generic JSON body above.

Client-side, `src/routes/__root.tsx`'s `ErrorComponent` and `src/lib/lovable-error-reporting.ts`
(`reportLovableError`) forward React error-boundary catches to the Lovable editor's telemetry hook
(`window.__lovableEvents`/`window.__lovableReportRuntimeError`), since production React does not
rethrow boundary-caught errors to `window.onerror`. `src/lib/error-page.ts` holds the shared fallback
HTML (`renderErrorPage`) used by both `start.ts` and `server.ts`.

When touching error handling, keep all three server-side layers in mind — a fix in one place
without the others can silently stop covering the h3-swallowed case.

### UI components

`src/components/ui/` is shadcn/ui (see `components.json`: "new-york" style, slate base color, CSS
variables, no prefix). Path aliases (`@/components`, `@/lib`, `@/hooks`, `@/ui`) are configured in
both `components.json` and `tsconfig.json` (`@/*` → `./src/*`). Regenerate/add shadcn components
through the shadcn CLI rather than hand-rolling equivalents, to stay consistent with the existing
set.

### Linting/formatting

- ESLint (`eslint.config.js`) bans importing the `server-only` npm package — this project uses
  `@tanstack/react-start/server-only` or a `*.server.ts` filename convention instead for
  server-only modules.
- Prettier is run through `eslint-plugin-prettier` as part of `lint`, not just via `format`.
- `@typescript-eslint/no-unused-vars` is disabled.
